OFFICIAL SENSEN CODE POLICY — BINDING AND NON-NEGOTIABLE
========================================================================
This document is the AUTHORITATIVE, OFFICIAL code policy for the sensen
repository. Every rule below is MANDATORY and MUST NOT be violated. It
governs ALL code: C++23, CUDA, and Python bindings, written by anyone
(humans or AI lanes) in any branch or worktree.

Enforcement (hard gate — no exceptions):
- Every code-writing task MUST be given this policy and MUST comply.
- Every mandatory dual review (Claude + agy, per config/update_policy.txt)
  MUST verify compliance rule-by-rule and FAIL the review on any violation.
- A merge is BLOCKED while any violation remains — kick the lane back and
  fix-forward; never merge a known violation, never "fix later".
- Where this policy and config/update_policy.txt overlap, both bind; where
  they conflict, the STRICTER requirement wins.
- Rule 39 (no external test framework) and Rule 50 (canonical build flags)
  are common trip-wires — check them explicitly on every change.
- Rule 64 (design principles: separation of concerns, encapsulation,
  cohesion/coupling, DRY, KISS, single responsibility, abstractions, YAGNI,
  composition, open/closed) governs STRUCTURE — every review answers its
  questions for the diff, and a structural violation blocks a merge like any other.
  Prefer Bf16 for all training, bf16 for adamw with momentum for optimisation otherwise fp32
  for optimisation. Likely weights are in fp32 as inputs. Multiprecision training in general
  to maximise bandwidth and reduce computational overheads.

CMakeLists.txt:541 defines it as an opt-out (`option(SENSEN_USE_LIBCXX ... ON)`, added in commit 5623901f) so a parent project can `add_subdirectory(sensen)` with it OFF and keep the WHOLE tree — including the vendored fastjson and logger submodules — on its own libstdc++ instead. A caller that sets SENSEN_USE_LIBCXX OFF takes on the obligation to hold it OFF consistently for its entire build (never flip it per-target) and to track when its own migration to libc++ is verified. This backend (OptionsAndFuturesCalculator) is exactly that caller today, mid-migration to libc++ — the option is expected to become unused once every consumer is confirmed on libc++, and REMOVING it then, restoring an unconditional -stdlib=libc++ so CMake matches this rule exactly, is the clean end state. Do not remove a working escape hatch before that migration is verified.

51. LIBC++ RESOLUTION VIA TOOLCHAIN WATERFALL — MANDATORY (Last Updated: August 2026, corrected). Never use system-provided std.cppm or libc++ headers picked up implicitly from an unqualified/hardcoded system path — resolve them explicitly through the waterfall below so every scope in one build agrees on exactly one libc++ install. There is NO vendored libc++ tree in this repo: no modules/std.cppm, no external/libcxx-v1/include/. Neither has ever existed — they were not removed, `git log --all` shows zero commits ever touching either path. A future reader should not go looking for a vendored copy; there isn't one to find.
    What the build actually does (CMakeLists.txt:307-347, non-MSVC only), run once at configure time:
    - The std module file (std.cppm) is located by a three-step waterfall: (1) Homebrew's libc++ at /home/linuxbrew/.linuxbrew/share/libc++/v1/std.cppm; else (2) <llvm-root>/share/libc++/v1/std.cppm, where <llvm-root> is derived directly from the ACTIVE CMAKE_CXX_COMPILER's own path (.../llvm-NN/bin/clang++ -> .../llvm-NN) — this is what makes apt.llvm.org's clang-23 work with no manual /usr/local/share symlink; else (3) /usr/local/share/libc++/v1 as a last-resort guess (CMakeLists.txt:307-325).
    - The matching runtime libc++ library path is located by a second, independent waterfall: ENV{LIBCXX_PATH} -> Homebrew -> /usr/local/lib -> /usr/lib/x86_64-linux-gnu -> /usr/lib -> a /usr/local/lib fallback that also emits a configure-time WARNING if none of the above exist (CMakeLists.txt:329-347).
    - The resolved std.cppm is precompiled ONCE into ${CMAKE_BINARY_DIR}/std_modules/std.pcm using the exact same flags every other target uses (rule 50), and that one std.pcm is what every module-consuming target in the tree resolves against.
    Why a waterfall instead of a hardcoded path: cloud boxes (Vast.ai, Packet, a fresh apt.llvm.org install) can have a different LLVM version installed than wherever CMakeLists.txt was last edited on; a hardcoded absolute path (e.g. /usr/lib/llvm-23/share/libc++/v1/) silently resolves to whatever happens to sit there, producing a partial build that fails deep in compilation with an opaque BMI error — wasting GPU $/hr before the mismatch surfaces. Deriving the path from the ACTIVE compiler, at configure time, is what keeps every scope in a given build on the SAME libc++.
    This is the exact discipline SENSEN_USE_LIBCXX (rule 50) protects one level up: a per-build libc++-VERSION mismatch (this rule) and a per-project libc++-vs-libstdc++ IMPLEMENTATION mismatch (SENSEN_USE_LIBCXX) are the same family of hazard — inconsistent standard-library configuration linked into one binary — and it is exactly the class of bug that broke when this backend (OptionsAndFuturesCalculator) first embedded sensen. Mixing standard libraries, at either the version or the implementation level, is a link-time hazard that shows up as an opaque symptom naming neither library, not a clean compiler error. Resolve to ONE libc++, consistently, for every scope in a build.

52. EXPLICIT MODULE FILE PATHS — NUANCED, CORRECTED (April 2026, corrected August 2026 against measurement). Every one of this tree's ~256 sensen-module PCM dependencies IS already resolved via explicit `-fmodule-file=<name>=<exact-path>` — not by hand-written discipline, but because CMake's own Ninja dyndep module scanner generates one `<TU>.o.modmap` response file per translation unit for any target using `FILE_SET CXX_MODULES` (verified directly: `build/src/CMakeFiles/sensen_objects.dir/autograd.cppm.o.modmap` lists 12 lines of exactly `-fmodule-file=sensen.X=<path>`, zero directory-search reliance). This is CMake 4.x's default behavior for a C++23-modules target; the project gets it for free, it never had to opt in.
    The ONE deliberate, unconditional exception is `import std;` itself. `CMAKE_CXX_FLAGS` carries `-fprebuilt-module-path=${STD_MODULE_OUTPUT_DIR}` (CMakeLists.txt:1007, redundantly re-added at src/CMakeLists.txt:33) on every non-Windows target, applied to sensen's own ~256 modules too, not just the vendored logger. It exists because `std.pcm` is precompiled by a hand-written `add_custom_command` (`std_module_precompile`) that sits OUTSIDE CMake's module-dependency scan, so it never gets a generated modmap entry naming it — the blanket flag is the only mechanism available to reach it.
    Verified safe here, not merely convenient: `${STD_MODULE_OUTPUT_DIR}` (`build/std_modules/`) holds exactly ONE file, `std.pcm`, produced by exactly one custom command scoped to that one build tree — there is no second candidate for the search to silently prefer. Its build flags (`STD_PCM_FLAGS`, CMakeLists.txt:1204-1238) are MECHANICALLY RE-DERIVED from the SAME `CMAKE_CXX_FLAGS` every consumer compiles with (with only `-fprebuilt-module-path`/`-fmodule-file` themselves stripped back out), so it cannot silently drift out of flag-sync with its consumers the way a hand-maintained duplicate flag list could; Ninja's own command-line-hash rebuild rule forces a rebuild the moment those derived flags change on reconfigure. The illustrative danger this rule used to cite — "modules/ canonical + modules_experimental/ AVX-512 variant coexisting" — describes a scheme that has never existed in this repo (`git log --all` shows zero commits ever touching either path); do not go looking for it.
    The vendored `logger` target (CMakeLists.txt:1312,1318) additionally gets an EXPLICIT `-fmodule-file=std=<path>` override on top of the blanket flag. This is NOT a defense against a stale/mismatched BMI — it exists because `logger` declares its own `FILE_SET CXX_MODULES`, which makes CMake want to link it against the special `__CMAKE::CXX23` std-module target (only created when `CMAKE_CXX_MODULE_STD` is ON); since this repo manages `std.pcm` by hand, `CXX_MODULE_STD` is forced OFF on that one target and the exact path is pinned directly so its `import std;` still resolves. 65. UNIVERSAL CUDA STREAM SEMANTICS AND STREAM 0 PURITY (owner, 2026-10-06; one definition per type is rule 64 DRY).
    65.1 NULLPTR HAS EXACTLY ONE MEANING: `nullptr` (or literal 0 / NULL) in any stream argument, bridge function, or kernel launch across the entire codebase means exactly one thing: NVIDIA CUDA legacy default stream 0. It NEVER means `get_default_stream()`, the engine stream, or an ambient stream.
    65.2 NO SILENT SUBSTITUTION: Never silently replace `nullptr` with `get_default_stream()` or `sensen_cuda_get_default_stream()`. If an API argument receives `nullptr`, it must dispatch to legacy stream 0 or preserve explicit `nullptr`. Where code requires `get_default_stream()`, the caller must pass it explicitly or name the symbol.
    65.3 CROSS-STREAM FENCING: Work issued to `get_default_stream()` (created with `cudaStreamNonBlocking`) does NOT synchronize implicitly with legacy stream 0 or other non-blocking streams. Code crossing stream boundaries (e.g. allocating or freeing on one stream and consuming on another, or downloading data populated by another stream) MUST explicitly fence via `cudaEventRecord`/`cudaStreamWaitEvent` or `cudaStreamSynchronize`. Unstreamed synchronous helper calls (`cudaMemcpy`, `cudaMemset`) that serialize the host or race against non-blocking streams are forbidden in active inference/training paths.
    65.4 MEMORY POOL STREAM RECORDING: Any buffer allocated from or recycled by the caching pool (`sensen_cuda_pool`) that is accessed on a stream other than its allocating stream MUST be registered via `sensen_cuda_pool_record_stream(ptr, stream)` before work is enqueued, ensuring subsequent allocations fence against all streams that touched the block.
    65.5 GRAPH CAPTURE INTEGRITY: During CUDA graph capture (`cudaStreamBeginCapture`), no synchronous stream operations or un-captured event waits may be issued to the capturing stream. Synchronization helpers (`sensen_cuda_synchronize`) must verify capture status before synchronizing streams.
    GATE: Static scanner `tools/check_cuda_stream_policy.sh` (enforced via `tools/policy_check.sh`), concurrency stress gate `tests/test_cuda_stream_ordering.cu`, and cross-stream reuse gate `tests/test_cuda_pool_cross_stream_reuse.cu`.

66. NO LEAKY ABSTRACTIONS (owner 2026-10-07; extends Rule 64.2 Encapsulation and the Law of Demeter). An interface exposes WHAT it does, never HOW one implementation does it. Callers interact exclusively with stable domain concepts; concrete implementation mechanics, vendor types, and internal invariants are hidden behind the boundary.
    Defect list (any of the following in a public or exported signature is a defect and blocks completion):
    - A backend or vendor type in a generic signature (e.g. `PGconn*`, `sqlite3*`, `MYSQL*`, `SQLHDBC`, `cudaStream_t`, `nb::object`, or Clang AST types outside the plugin boundary).
    - A dialect, wire format, or physical layout that the caller must speak through a supposedly neutral API (e.g. raw SQL query text, dialect-specific placeholder syntax, column offsets, or storage file layout).
    - Exposing mutable references, raw pointers, or iterators directly into internal storage (such as returning a reference to an internal container or an engine's internal `std::optional` state).
    - An implementation error code or vendor error enum instead of the interface's own domain error type.
    - A required temporal call order (such as init(), open(), then use) that the type system does not enforce through RAII or typestate.
    - A capability that the caller can only learn by trying and failing, rather than negotiating capabilities upfront through typed queries.
    - Silent fallback that conceals which path ran: an invalid chain or configuration is an error at build() or run() time via `std::expected`, never a quietly substituted default that hides failure.
    The second-implementation test: could a SECOND implementation (e.g. SQLite vs PostgreSQL vs MySQL for storage, or CPU vs CUDA for compute) satisfy this signature unchanged, and could a caller switch between them without editing call sites? If not, the abstraction leaks.

67. EVERY CODE NAME A DOC CITES MUST EXIST IN THE CODE (owner 2026-10-12). A document is part
    of the deliverable, so an invented name in it is a defect of the same kind as an invented
    function in code, and it is worse in one way: the next reader TRUSTS it, so a stale note
    recording why something is impossible is the one they believe instead of measuring. On
    2026-10-07 a docs lane's report marked every citation "verified" while its docs named
    functions, files and error strings that do not exist. GATE: `tools/check_docs_claims.py`
    reads the Markdown lines a branch ADDED, takes every backticked span that names code (an
    identifier, a qualified name, a flag, an environment variable, a repository path, a quoted
    message, a git revision, a command line) and looks it up in this repository's own tracked
    files outside docs/ and *.md -- the tree is read once and every lookup is answered in
    memory (a revision is the one exception: it asks git), so a doc with a thousand citations costs
    one pass over the repository:

      python3 tools/check_docs_claims.py                   # lines added since the default branch
      python3 tools/check_docs_claims.py --base REV         # ... since REV
      python3 tools/check_docs_claims.py --all FILE.md ...  # whole files
      python3 tools/check_docs_claims.py --json             # machine-readable
      bash tools/test_check_docs_claims.sh                  # the gate's own gate, on a throwaway repo

    Four buckets. MISSING is fatal (exit status 1): the name is not in this repository. DESIGN
    (inside a heading section or top-level list entry marked "Design (not built)"), FRAGMENT
    (two backticks paired across a sentence -- a Markdown defect) and REVISION (a commit this
    repository cannot resolve, i.e. another repository's) are reported and never fatal. A
    commit that changes a *.md runs the gate and leaves MISSING at zero, or lists every
    remaining line WITH its justification in the commit message or lane report; another
    repository's code names and kernel/external-tool names are that justified class, and a
    lane's own statement that its citations were verified is not evidence. LIMIT, stated
    because it is the half this cannot do: the lookup is TEXTUAL, so a pass proves the cited
    name EXISTS, not that the sentence around it is true -- the semantic fact-check is still a
    human's. Nothing in it is specific to one repository: the base is derived from this
    repository's own default branch (origin/HEAD, else origin/master, else origin/main) and the
    path prefixes from its own tracked top-level directories, because a recorded list is right
    for one tree and silently skips every citation outside it. The COPY OF RECORD is sensen's
    `tools/check_docs_claims.py`; sensen, OptionsAndFuturesCalculator, ThinButQuickWebFramework,
    mortgage-nest-egg, fastestjsoninthewest and cpp23-logger each carry a BYTE-IDENTICAL copy.
    Change sensen's and copy it out; never edit a copy in place. Nothing in a consuming
    repository can compare the two today -- OptionsAndFuturesCalculator's backend/sensen pin
    predates the script -- so that rule is kept by hand, and the self-test is the only local
    proof that the copy where it sits works.

68. A TOOLCHAIN PATH IS RESOLVED ON THE HOST, NEVER WRITTEN DOWN (2026-10-15). An absolute
    compiler path is required -- bare `clang++` resolves through PATH and has landed on a clang
    below the floor and on a ccache shim, and the std.cppm walk follows the ACTIVE compiler's
    own directory -- but WRITING ONE DOWN fails the other way, and on 2026-10-15 it had: every
    documented configure command in this tree, CLAUDE.md and its four mirrors among them, named
    a versioned LLVM root absent on the box those pages are written on, so the documented
    command died in CMake on a missing compiler. Fourteen script defaults named the same path.
    This is rule 50's floor with a path in place of a number, and the same correction: the
    number is checked by `tools/check_toolchain_floor.sh` because correcting it by hand reached
    four of seven places. Live instructions and executable defaults name a RESOLUTION:

      CXX=$(tools/compiler_path.sh c++) CC=$(tools/compiler_path.sh c)
      cmake -G Ninja -B build -DCMAKE_CXX_COMPILER="$CXX" -DCMAKE_C_COMPILER="$CC"

      python3 tools/check_compiler_paths.py       # no live instruction names a literal path
      bash tools/test_check_compiler_paths.sh     # that gate's own gate

    `tools/compiler_path.sh` reads the floor from CMakeLists.txt rather than restating it,
    verifies `clang version N` against it, refuses a ccache/distcc shim (a shim answers
    `--version` as the compiler it wraps, so the discriminator is what the file IS) and does
    NOT resolve the final symlink, because clang picks its C or C++ driver mode from the name
    it is invoked as. Python callers use `tools/sensen_toolchain.py`, one definition per rule 64.
    WHAT IS NOT A DEFECT, because the gate's first version reported all of it: a path derived
    from a variable, a guarded probe, a candidate list, an `update-alternatives` that CREATES
    the path, a table row, prose, and a DATED RECORD -- a session log, a handoff, a
    `*_RESULT.md`, a changelog, a benchmark report. Editing a record of what was run does not
    fix anything; it makes the record false. Six live lines carry an inline
    `compiler-path-ok: <reason>` waiver, printed and counted on every run.

69. A SUBMODULE PIN IS A DEPENDENCY STATEMENT AND IS GATED LIKE ONE (2026-10-16). The commit a
    superproject records for a submodule is the ONLY place that dependency's version is stated,
    and on 2026-10-16 that statement was false: `agent/src/gateway_tbqwf.cppm` consumed
    `tbqwf::http::TransportError`, introduced in TBQWF `96b35ca7`, while `external/tbqwf` was
    pinned 314 commits behind it -- so `sensen-gateway` COULD NOT BE BUILT FROM A CLEAN CHECKOUT.
    Three more modules were in the same state; `agent/src/gateway_tls_reload.cppm` and its test
    named four further absent names. It survived because every developer tree built: each had
    fetched the submodule ahead of the pin for some other reason, so the pin was the one thing
    no one's build ever used. This is rule 67 with a dependency in place of a document -- a name
    cited must exist where it is cited from -- and it takes the same answer:

      python3 tools/check_submodule_api.py        # every submodule name spelled must exist AT THE PIN
      bash tools/test_check_submodule_api.sh      # its own self-test
      ctest -R 'check_submodule_api'              # both, registered

    Three properties the gate must keep, each because losing one makes it useless rather than
    wrong: it reads the INDEX and never the submodule's worktree; it resolves namespace aliases;
    and it reports ABSENCE ONLY. The reasoning for each, and the list of spellings it does NOT
    see, live in the tool's docstring beside the code that implements them -- not repeated here,
    because a rule and a docstring that explain the same mechanism twice will disagree once.

    MOVING A PIN IS A RELEASE DECISION, NOT A FIX. The correction here moved a submodule 314

70. A MODULE INTERFACE MUST NOT DEMAND A FEATURE ITS BASELINE ALREADY PROVIDES (2026-10-16).
    Clang records the EXPLICIT target-feature list in a BMI and the compatibility check is
    ONE-DIRECTIONAL: a BMI naming `+fma` is refused by any translation unit that does not name it
    too, while a BMI naming FEWER features loads happily in a consumer naming more. `-march=` is
    NOT interchangeable with `-m<feature>` for this purpose -- `-march=x86-64-v3` enables FMA and
    defines __FMA__, yet emits no `-target-feature +fma` to cc1 -- so a consumer on the IDENTICAL
    baseline, spelled that way, is told it "is not" compiled with +fma and every name in the
    module disappears.

    A redundant `-m<feature>` on a module target therefore buys no instruction and exports a
    requirement, in that exact spelling, to every consumer. One of them, added upstream in
    fastestjsoninthewest on 2026-10-14 for internal consistency, stopped ThinButQuickWebFramework
    building two days later at src/ads/answer.cppm on the same x86-64-v3 baseline. A feature worth
    having belongs in the baseline, where every consumer inherits it from `-march=`, or in an
    implementation translation unit, which exports no BMI.

      bash tools/check_module_bmi_features.sh <configured build dir>
      ctest -R check_module_bmi_features

    THE GATE ASKS THE COMPILER, not an ISA table, which features a command's own `-march` already
    implies, because that is the only way to tell a redundant flag from a deliberate floor raise:
    `-maes -mpclmul` are NOT in x86-64-v3, so they genuinely add instructions and genuinely raise
    the floor, and calling that a defect would make the gate noise in a tree that needs them. It
    reads the build directory's COMMANDS rather than its target list, because a BMI is produced
    through dyndep and the static list holds only the std modules -- the first version of the gate
    scanned 4 precompiles, none of this tree's, and passed on the defect it was written for.

    IT IS REGISTERED AS A RATCHET AND THE WAIVER IS A DEBT. This tree's 1164 module interfaces all
    raise the baseline by `-maes -mpclmul`, inherited with TBQWF; 708 of them also carry `-mfma`
    from CANONICAL_FLAGS and 456 do not, the shared std.cppm among the 456. Two spellings coexist,
    and the build survives only because the direction is safe -- the no-FMA side is imported BY the
    FMA side, never the reverse. An import crossing the other way stops the build.
